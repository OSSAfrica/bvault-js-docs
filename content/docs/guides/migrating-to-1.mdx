**Published prerelease:** this guide covers upgrading from 0.x to **1.0.0-preview.0**, available on the `preview` tag. Choose npm, pnpm, or Bun in the [preview installation guide](/docs/next#install-the-preview). The npm `latest` tag remains 0.3.4. Read the [prerelease notes](https://github.com/OSSAfrica/bvault-js/releases/tag/bvault-js%401.0.0-preview.0) before testing the upgrade; stable 1.0.0 is still tracked in [library #29](https://github.com/OSSAfrica/bvault-js/issues/29).

## Before the first new initialization

The preview `initializeSecureStorage()` invokes legacy-data cleanup. It removes localStorage/sessionStorage values identified by legacy IndexedDB metadata. This is **deletion, not automatic decryption and re-encryption**. Unrelated application entries are not intentionally cleared.

The library supplies no built-in encrypted-data migration. If your application still knows the old password and can read its data with the old version, preserve required data **before running the new initialization**. Otherwise refetch it from a trusted source. Do not try unknown passwords against old values: 0.3.4 deletes a value on failed reads.

## API changes

| Stable 0.3.4                        | 1.0.0-preview.0                                                           |
| ----------------------------------- | ------------------------------------------------------------------------- |
| Password required at initialization | No password argument                                                      |
| Public encrypt/decrypt              | Removed                                                                   |
| Caller's raw storage keys           | `bv1:`-prefixed keys                                                      |
| IV/salt metadata stores             | Generated key in IndexedDB; versioned ciphertext payload                  |
| Read failure removes the value      | Read failure preserves the value                                          |
| clear clears entire Storage         | clear removes bVault-owned entries                                        |
| No destruction export               | destroySecureStorage deletes the persisted key and current-context values |

## Rollout checklist

1. Verify the actual published target package and read its changelog.
2. Inventory the data your application currently stores and which values can be refetched.
3. Preserve any required legacy data while the old password, old library, and metadata are still available.
4. Test the transition in an isolated browser profile or non-production origin.
5. Upgrade, initialize without a password, and repopulate the new cache.
6. Test reloads, storage-denied/key-loss states, and your account-switching policy.

Rolling the package version back does not restore deleted data. Do not assume a browser-profile copy or a second tab provides a safe recovery path.

## Logout and key loss

The preview destruction API deletes the key, so ciphertext under it cannot be recovered without that key. In the published **preview.0** version, other tabs can retain cached key handles. [Library #9](https://github.com/OSSAfrica/bvault-js/issues/9) is fixed in the source staged for **preview.1**, pending npm approval; see [cross-tab lifecycle changes](/docs/next/development#cross-tab-destruction). Applications must still coordinate their own authentication/account state rather than treating key deletion as server-side session revocation.

Review the [actual migration source](https://github.com/OSSAfrica/bvault-js/blob/bvault-js%401.0.0-preview.0/src/lib/migration.ts) and [tests](https://github.com/OSSAfrica/bvault-js/blob/bvault-js%401.0.0-preview.0/test/migration.test.ts), along with the [preview API](/docs/next/api).
